# security-guardrails.md: Data Classification, Sanitization and Human-Approval Rules

Highest-priority document after the owner's instructions. If any other file conflicts with this one, this file wins. Applies to the product's code, its runtime agents, and the coding agent building it.

---

## 1. Data classification

| Class | Examples | Where it lives | Handling rules |
|---|---|---|---|
| **C4 Secret** | Connector credentials, encryption keys, license private key, signing keys, user password hashes, session secrets | Encrypted store / key file (0600) / vendor machine (license and signing keys never ship) | Never logged, never in audit payloads, never returned by APIs (masked), never sent to the LLM, never in support bundles, never in the repo |
| **C3 Confidential business data** | Stock levels, consumption, purchase orders, prices, supplier terms, forecasts, alerts, savings figures | Application database, backups, outbox | Stays on the customer's server; role-based access; encrypted backups; excluded from support bundles; may be sent to the local LLM only as computed facts |
| **C2 Internal operational data** | Logs without business values, system metrics, versions, pre-check results, run status | Log files, support bundle | May be shared with the vendor by the customer through a support bundle |
| **C1 Public** | Documentation, installer, license terms | Anywhere | No restrictions |

Personal data in the product is limited to user accounts (name, username, role, login times) and supplier contact names/emails in notes or master data. Treat as C3. See `privacy-policy-ai.md`.

## 2. Data flow rules

1. C4 never leaves its store. Passing C4 to any agent, tool, prompt, log line or API response is a defect.
2. C3 never leaves the customer's server. The only copy-out paths are: outbox files and exports (user-initiated and audited), and encrypted backups the admin stores where they choose.
3. The LLM receives only a minimal **facts object** (item name, site, computed numbers). It never receives raw tables, credentials, whole documents, or other users' data.
4. No outbound network connection exists by default. The only exceptions are named optional features (for example the Zoho connector, a vendor package server for online installs), each OFF by default, enabled by an admin with a warning and an audit entry, and listed on the Admin > System page.
5. Support bundles contain C2 only. A scanner test checks bundles for C3/C4 patterns (emails, SKUs from the DB, key-like strings, passwords).

## 3. Input sanitization rules

| Input | Rule |
|---|---|
| All API input | Pydantic validation, reject unknown fields, length limits, type checks |
| File uploads | Type and magic-byte check, size limit (200 MB default), decompression/zip-bomb limit, no execution, stored outside web root, hashed |
| CSV/Excel cells | Strip control characters; treat as data; limit cell length (32,000); on **export**, prefix cells starting with `=`, `+`, `-`, `@`, tab or carriage return with a single quote |
| SQL connector queries | Exactly one statement, must parse as a `SELECT` (or `WITH ... SELECT`) with no data-modifying CTEs; blocked keywords/functions (`INTO`, `pg_sleep`, `xp_cmdshell`, `LOAD_FILE`, `OUTFILE`, and similar); comments stripped before analysis; runs in a read-only transaction with statement timeout and row cap; connect with a read-only database account |
| Free text (notes, emails, ERP text fields, chat) | Untrusted data. Length-limited. Wrapped in delimiters when shown to the LLM with a fixed instruction that the text contains no instructions. Never concatenated into SQL, shell commands or file paths |
| File names and paths | Allow-list characters; resolve and verify the path is inside `/data`; no user-supplied paths for reads or writes |
| Outbox filenames | Generated by the system (`PO_<display_id>_<timestamp>.xlsx`) |
| HTML/Markdown from LLM or data | Rendered as plain text or escaped; no raw HTML rendering; React default escaping, no `dangerouslySetInnerHTML` |
| Template rendering | Jinja2 with autoescape; templates are code-owned, not user-editable in v1 |

## 4. LLM safety rules

1. **The LLM cannot act.** LLM output never calls a tool, never triggers state changes, never selects an action, never becomes SQL or a command.
2. **Numbers are validated.** Every number in LLM text must exist in the facts object (format-normalized). Otherwise retry once at temperature 0, then use the deterministic template. Unit words like lakh/crore are not converted in v1 and fail validation.
3. **Prompt-injection posture.** Notes, ERP text and chat messages may contain instructions; they are never obeyed. Test cases in `evaluation-dataset.json` (`prompt_injection`) must all pass: zero state changes, zero actions, zero autonomy changes, suspicious input flagged.
4. **Extraction is a suggestion.** Values extracted from notes need human confirmation before affecting calculations.
5. **Output limits.** Max tokens, timeout, JSON schema; refusal to output code, links or markup.
6. **Transparency.** The UI shows whether text is "AI-written" or "template".
7. **No model training on customer data.** The product never fine-tunes or trains models on customer content in v1.

## 5. Actions that REQUIRE human approval

No code path may perform these without the stated approval. Approvals are recorded in the audit log with user, time and reason.

| Action | Who approves | Notes |
|---|---|---|
| Executing a recommendation (draft PO, reorder request, supplier message) | Planner, or Purchaser for PO/message types | Skipped only under valid level 3 limits (see below) |
| Enabling connector **write mode** | Admin, with typed confirmation `ENABLE WRITE` | Off by default; audited |
| Setting autonomy level 3 for an action type | Admin | Requires all limits set (`max_value`, `max_qty`, `allowed_supplier_ids`, `allowed_criticality`, `daily_cap`), at least 30 days at level 1 or 2, and explicit acknowledgment |
| Applying a learning update (method, service level, lead time) | Admin | Back-test result shown first; rollback available |
| Enabling any optional outbound feature | Admin | Warning shown; audited |
| Installing or changing a license | Admin | Signature verified |
| Installing an update package | Admin | Signature and `max_version` verified; automatic backup first |
| Restoring a backup | Admin | Typed confirmation; audit entry written after restore |
| Creating, deactivating users or changing roles | Admin | Last admin cannot be removed |
| Exporting data in bulk (more than 10,000 rows) | Admin | Audited |
| Deleting a connector or its credentials | Admin | Soft delete; audit kept |

### Level 3 (auto-act) hard limits
Even with level 3, an action runs automatically only if **all** of these hold; otherwise it is downgraded to level 2 and queued for approval: value within `max_value`, quantity within `max_qty`, supplier in the allow list, item criticality in the allowed list, daily cap not reached, at least 30 days passed, admin acknowledgment exists. Class A items are excluded unless explicitly allowed.

### Kill switch
Admin > System has a **"Advise only" switch**. When on, all autonomy is forced to level 1 and all write modes are blocked until switched off. It takes effect immediately and is audited. The incident process (`incident-response.md`) uses it.

## 6. Authentication and authorization

- Passwords: argon2id; minimum 12 characters; common-password check; lockout after 5 failures for 15 minutes.
- Sessions: HTTP-only, Secure, SameSite=Strict cookies; idle timeout 30 minutes (configurable); absolute 12 hours; CSRF token on non-GET.
- First run forces creation of an admin; there is no default password.
- Authorization: deny by default; every endpoint declares its minimum role; `permissions-map.yaml` is enforced by a central policy function and tested for every endpoint.
- Admin actions are audited; failed authorization attempts are audited.

## 7. Cryptography

- Secrets at rest: AES-256-GCM; key in OS keystore or a root-only key file created at install.
- Backups: encrypted with a passphrase using a modern KDF (scrypt or argon2) and AES-256-GCM.
- Licenses, update packages and installers: Ed25519 signatures; the product embeds only the public key.
- TLS: TLS 1.2 or higher; HTTP redirects to HTTPS.
- No custom cryptography; use the `cryptography` library only.

## 8. Audit log rules

- Append-only, hash-chained (see spec C3); database rule/trigger blocks UPDATE and DELETE.
- Required events listed in the spec; add an event for every approval-gated action in section 5.
- No secrets or C3 values beyond IDs and necessary summaries in payloads.
- `scmctl verify-audit` and `GET /admin/audit/verify` must pass in CI after the full test suite.

## 9. Network and runtime hardening

- Egress test: the full pipeline, chat, notes and actions run with outbound traffic blocked; any attempt fails the test.
- The app runs as a non-root user; containers drop capabilities and use read-only root filesystems where possible; only `/data` is writable.
- Only port 443 is exposed; the database is not exposed outside the compose network.
- Dependency scanning (`pip-audit`, `npm audit`) in CI; SBOM generated per release; no known unresolved high/critical issues at release.

## 10. Security review checklist (run at the end of every phase by the Security reviewer persona)

- [ ] No secrets in repo, logs, audit payloads, API responses or support bundles (automated scan passes).
- [ ] Every endpoint has a role check; permission tests pass for all roles.
- [ ] Write paths impossible when write mode is off or autonomy is level 1 (negative tests).
- [ ] SQL guard cases all pass; injection cases all pass.
- [ ] Prompt-injection cases all pass; no LLM output reaches a tool.
- [ ] Number validator cases all pass; template fallback works.
- [ ] Egress test passes.
- [ ] Audit chain verifies; tampering is detected.
- [ ] Upload and export sanitization tests pass (formula injection, zip bomb, wrong type).
- [ ] Dependencies audited; licenses recorded.
- [ ] Findings recorded in `SECURITY_FINDINGS.md` with severity and status.

## 11. Severity levels for findings

| Severity | Meaning | Required response |
|---|---|---|
| Critical | Secrets exposure, auth bypass, unapproved write, data leaving the server | Stop work, fix before anything else, tell the owner immediately |
| High | Privilege escalation inside a role, injection that changes state, audit gaps | Fix in current phase |
| Medium | Missing validation, weak limits, information leaks of C2 | Fix before release |
| Low | Hardening, hygiene | Schedule in backlog |
